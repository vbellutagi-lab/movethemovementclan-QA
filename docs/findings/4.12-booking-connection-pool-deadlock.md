# P0 — Concurrent bookings permanently deadlock the entire API

**Repo to fix:** `movethemovementclan` (the app, not the QA repo)
**Found by:** `movethemovementclan-QA` → `src/integration/bookings/capacity.test.ts`
**Catalogued as:** `docs/scenarios.md` §4.12

---

## Summary

Ten concurrent `POST /api/bookings` requests permanently deadlock the API. Every
database-backed route hangs forever afterwards. There is no timeout and no self-recovery —
the API process must be restarted.

The trigger is ordinary user behaviour: a popular class opening for booking. No authentication
bypass, no malformed input, no unusual payload. Just ten people booking at the same moment.

---

## Reproduction

1. Pick any bookable session with capacity ≥ 1.
2. Have 10 distinct signed-in clients, each holding ≥ 1 eligible credit, `POST /api/bookings`
   for it simultaneously.
3. No response ever returns.
4. `GET /health` still answers in <1ms (it touches no database), while every DB-backed route
   times out. That asymmetry is the signature of connection-pool starvation rather than a
   crashed process.

Observed live on a local dev instance; the wedge persisted for 12+ minutes until restart.

---

## Evidence

`pg_stat_activity` during the wedge:

```
        state        | wait_event_type |  wait_event   | n | longest_in_state
---------------------+-----------------+---------------+---+------------------
 active              | Lock            | tuple         | 8 | 00:11:45
 active              | Lock            | transactionid | 1 | 00:11:45
 idle in transaction | Client          | ClientRead    | 1 | 00:11:45
```

- The single `idle in transaction` backend's last statement is
  `insert into "bookings" ... on conflict ("idempotency_key") ...` — it got as far as the
  insert, still holds the `sessions` row lock, and Postgres is now waiting to hear from the
  application (`ClientRead`).
- The other nine are all parked on `select ... from "sessions" ... for update`, behind it.

---

## Root cause

`packages/services/bookings/charge-strategy.ts:30` calls `credits.pickCreditLot(...)` from
inside the booking transaction — but `pickCreditLot` takes **no `tx` parameter at all**
(`packages/services/credits/index.ts:91`). It is documented as a "pure decision", so it reaches
`DrizzleCreditRepository.findAvailableLots` (`packages/services/credits/repository.ts:181`),
which queries the **global pooled `db` handle**.

The very next call, `reserveCreditLot(tx, ...)`, does take the transaction. So the charge is
split across two connections.

### Why that deadlocks

The deadlock spans **two resource pools**, which is what makes it invisible to Postgres and
permanent.

1. Postgres row locks (`SELECT ... FOR UPDATE` on `sessions`).
2. The Node-side `pg` connection pool. `packages/database/index.ts:12` does
   `drizzle(env.DATABASE_URL, { schema })` with **no pool options**, so `pg`'s default applies:
   **`max: 10`**. The API has exactly ten connections, ever.

A transaction occupies one connection for its entire lifetime (`BEGIN` → `COMMIT`); it cannot
be shared or migrated. So every in-flight booking holds one connection and then, midway
through, **asks the same pool for a second one while still holding the first.**

With 10 concurrent bookings:

```
1. All 10 open transactions        → all 10 connections checked out. Pool empty.
2. One (A) wins the session row lock; the other 9 block waiting for A to commit.
3. A does the insert, reaches pickCreditLot, asks the pool for connection #11.
4. There is no #11. Connections are only returned when a transaction ends.
5. The other 9 cannot end — they are waiting on A's row lock.
6. A cannot end — it is waiting for a connection only they can free.
```

Circular wait. Nothing moves again.

### Why nothing breaks the cycle

Postgres's deadlock detector sees nothing wrong, because half the cycle is not in Postgres:

- The 9 blocked backends are legitimately waiting on a row lock held by an uncommitted
  transaction. Normal.
- A's backend is `idle in transaction / ClientRead` — from Postgres's side, just a slow client.

There is no lock cycle *within* Postgres, so `deadlock_timeout` never fires. With no
`statement_timeout` or `idle_in_transaction_session_timeout` configured, nothing ages it out.

### Why the cliff is exactly 10

It is `concurrency >= pool max`, and pool max is `pg`'s default of 10.

- **N = 9** — nine transactions hold nine connections, one spare remains. The winner borrows the
  spare, commits, releases both; the next proceeds. Serialized and slow, but it completes.
  (Verified: a 2 → 4 → 6 → 8 ramp passes.)
- **N = 10** — zero spare. The borrow can never succeed.

## The fix

Give `pickCreditLot` the transaction, so the whole charge runs on one connection and never
borrows a second. Blast radius is small: **one production caller each.**

### 1. `packages/services/credits/repository.ts`

Interface (line ~113):

```ts
findAvailableLots(
  tx: AppDbTransaction,
  clientId: string,
  creditType: string,
): Promise<(typeof creditLots.$inferSelect)[]>;
```

Implementation (line ~181) — swap the global `db` for `tx`:

```ts
async findAvailableLots(tx: AppDbTransaction, clientId: string, creditType: string) {
  return await tx
    .select()
    .from(creditLots)
    .where(
      and(
        eq(creditLots.clientId, clientId),
        eq(creditLots.creditType, creditType),
        gt(creditLots.remaining, 0),
      ),
    );
}
```

### 2. `packages/services/credits/index.ts`

Signature (line ~91) — `AppDbTransaction` is already imported for `reserveCreditLot`:

```ts
async pickCreditLot(
  tx: AppDbTransaction,
  rawInput: PickCreditLotInput,
): Promise<PickedCreditLot> {
```

Call site (line ~100):

```ts
const candidates = await this.repository.findAvailableLots(tx, input.clientId, input.creditType);
```

### 3. `packages/services/bookings/charge-strategy.ts` (line ~30)

```ts
const picked = await this.credits.pickCreditLot(tx, {
  clientId: input.clientId,
  sessionCentreId: input.sessionCentreId,
  creditType: input.creditType,
  now: input.now,
});
```

### 4. Update the now-stale comment at `packages/services/credits/index.ts:121-125`

It currently reads *"`pickCreditLot` reads outside any lock, so the picked lot may have been
spent by a concurrent booking in the meantime."*

> ⚠️ **Do not delete the guarded decrement in `reserveCreditLot` as part of this change.**
> After the fix `pickCreditLot` reads *inside* the transaction, but it still does **not** take
> `FOR UPDATE` on the credit-lot row — so the picked lot can still be spent concurrently, and
> the `remaining >= amount` guard in `decrementRemaining` is still load-bearing (ADR 0020).
> Only the wording about being "outside any lock" needs correcting, not the guard.

### Note on typing

`AppDbTransaction` is a type alias for `AppDatabase` (`packages/database/index.ts:10`), so any
caller that legitimately runs outside a transaction can pass the global `db` and still typecheck.
No call site needs restructuring.

## Defence in depth (separate from the fix above)

1. **Set pool timeouts.** `statement_timeout` and `idle_in_transaction_session_timeout` on the
   pool would convert any future bug of this shape from a permanent outage into slow failing
   requests. This class of bug is easy to reintroduce; the timeout is what stops it being an
   outage next time.
2. **Consider a lint/review rule**: a service method called from inside `db.transaction()` must
   not reach the global `db`. This bug is exactly one missing parameter, and nothing in the type
   system catches it.

### What will *not* fix it

**Raising `max` above 10.** That only moves the cliff to the new number. The structural problem
is holding one connection while requiring a second from the same pool; any bound can be reached.

## Verification

After the fix, from the QA repo:

```bash
npm test -- src/integration/bookings/capacity.test.ts
```

Expected: all six tests pass, including the two 10-client races (`exactly 3 of 10 win against
capacity 3`, and `all 10 win against capacity 10`). The suite prints per-request timings and a
total wall-clock figure for the parallel races.

Before the fix, the two 10-client tests fail with an explicit diagnosis after a 15s per-request
timeout, and the API needs a restart afterwards.

### One open question worth confirming

The captured trace was for 10 clients booking the **same** session, where row-lock contention is
genuinely part of the cycle. From the mechanism, 10 concurrent bookings of **10 different**
sessions should deadlock too — no row-lock contention at all, but all ten still hold one
connection and request an eleventh.

If that holds, the finding is broader than "concurrent bookings of one session" and is really
"any 10 concurrent bookings". Worth a test either way; it changes how urgent this looks, since
different-session concurrency is far more common in production than same-session contention.
