The headline finding. The codebase has a real, followed convention for this exact problem — identityProcedure's own doc comment in packages/trpc/server/trpc.ts says it outright: “there is no Postgres row-level security wired up… treat any client id arriving via .input() as untrusted.” Routes like bookings.cancel, booking-oversight.*, schedule-exceptions.*, and clients.enroll all follow it: they check the caller's own org/client id against the target row before acting, usually returning 404 (not 403) on a cross-org match so existence itself isn't leaked (ADR 0016, ADR 0035).

Three route families skip that check entirely. credits.*, classTemplates.*, and sessionTypes.* are gated by orgProcedure("admin") — the caller must be admin/owner of some org — but never verify the target object belongs to that org. Any studio's admin account is sufficient. No special privilege, no guessing beyond a UUID.

422

InsufficientCreditsError is declared as HTTP 422 — it is never actually 422 on the wire still open

packages/services/credits/error.ts declares it as ServiceError(422, …), and documents/architecture/booking.md's error table documents 422 too. But packages/trpc/server/utils/http-status.ts's HTTP_STATUS_TO_TRPC_CODE map has no tRPC error code for 422 — tRPC's own TRPCError only supports its fixed standard-code enum — and falls back to "BAD_REQUEST", which the OpenAPI adapter serializes as HTTP 400. A client can't distinguish “insufficient credits” from a generic validation error by status code alone — only the response body's message string differs. The same root cause affects any other ServiceError subclass whose declared status this map doesn't carry a 1:1 entry for. P2 — API-contract inconsistency, not a security issue.

🔑

Idempotency key alone is the dedupe identity — request parameters aren't checked still open

Reusing a booking's idempotency key with a different sessionId returns HTTP 200 with the original booking's data, not an error and not the new session. security.html §7 requires keys to be “bound to… request parameters” and reuse with different parameters to be rejected. Same bug as §3.6 — not a separate item, just surfaced twice. See src/integration/bookings/happy-path.test.ts.

200

Booking creation returns HTTP 200, not 201, despite the handler calling TRPCResponse.created() still open

trpc-to-openapi doesn't infer 201 from a mutation by itself, and nothing in the route's .meta() sets it explicitly. Cosmetic — but the response message (“Booking created”) and the status code now disagree about whether this was a creation.

11.3 — Test types never attempted, not just deferred

  • Injection/XSS/mass-assignment payloads (§3.2–3.4) — still reasoned-safe-from-code-reading only. Cheap to close; should be first, not last.
  • CORS/Origin enforcement — this suite's own ApiClient always sends a legitimate Origin header (Better Auth requires one); nothing here tries a disallowed origin to confirm the allowlist actually rejects it.
  • Contract/schema drift against the live OpenAPI spec (/openapi.json) — would have caught the §8 422→400 and 200→201 mismatches structurally, by diffing declared vs. actual, instead of by accident.
  • Accessibility — a real design system exists (documents/internals/design/); zero automated a11y checks (axe-core or equivalent) on any page.
  • Visual regression, cross-browser (Playwright is chromium-only), mobile viewport, load/perf beyond 2–3-way concurrency races — none attempted.

11.4 — Process gaps that will bite before any of the above does

  • No CI wiring at all. This entire suite has only ever run manually, from this session, against one long-lived local Postgres (6+ days uptime). It has never been proven to pass from a clean checkout.
  • No test-data isolation or teardown. Every run leaves behind throwaway orgs, users, and credit lots in that same database, permanently. There's no ephemeral-DB-per-run (Testcontainers or equivalent), so the suite's own footprint grows without bound.
  • Shared mutable seed accounts, no reset. owner@move.dev / coach@move.dev / client@move.dev are used across every file with no per-test isolation beyond picking distinct sessions manually — a genuinely broken test could leave state that fails an unrelated later one.
  • No coverage inventory. This document lists scenarios that exist; it has never been checked against a literal enumeration of every tRPC procedure in the app to confirm nothing shipped with zero test of any kind touching it.
